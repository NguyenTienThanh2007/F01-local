# F01 commercial-v1

Implemented on `codex/f01-commercial-v1`, continuing GitHub HEAD `8d4aa6051ef74d42d7b4f71736abc61fdef04cfa` and main `449b0588e072cda102144c0c629d776049b4f2d2`. Main is unchanged. Vercel prebuilt and the browser-only Next.js static-export profile were explicitly selected for this continuation. This is the bounded commercial-v1 application journey; billing, teams, connectors, app databases, server functions, custom domains and a public launch of the factory remain outside this scope.

The owner can create a real project, plan and approve, build/verify/repair inside trusted Docker, inspect its isolated preview, request a separate Vercel hosting target, prepare a production package, explicitly approve Deploy, and obtain an observed public URL. A change uses the existing pinned-source patch pipeline, produces a new preview, and requires a new production package and explicit redeployment. Preview, production and immutable versions/releases are separate. Historical inspection changes neither pointer.

## Execution and lineage

Phase 2B source generation, bounded repair, immutable candidates/evidence, leased execution and isolated preview are retained. Generated code never runs on the factory host. Containers have no host mounts, no Docker socket, no factory/release credentials, no external network, a read-only root, dropped capabilities, and enforced resource/lifetime limits.

Production packaging derives a separate trusted `next-static-v1` image from an exact accepted Phase 2B image. It reuses the immutable dependency tree, verifies it before applying the application-owned root-path/static-export configuration, reruns typecheck/build/tests, checks source/scaffold integrity, exports bounded regular files, and verifies the actual root page and version marker in the sandbox. No source is generated again for deployment. The factory validates data bytes without extracting or executing them. Functions, symlinks, path escapes, duplicate paths, corrupted digests, preview paths and outputs over 16 MiB/2,000 files are rejected.

The immutable PostgreSQL package/manifest binds project, source candidate/digest/parent, source lineage, version, published Brain revision, request, plan, source evidence IDs/digests, exact production image, dependency lock, production configuration, output digest, production evidence and health marker. Durable package bytes do not depend on preview container lifetime or provider retention.

## Releases and recovery

Additive migrations `0004_phase2c`–`0006_release_hardening` add production configuration, preparation, package, target, intent, operation, observation and provisioning records. Frozen `0001`–`0003` are untouched. Same-project constraints, immutable history/results and active-release guards protect existing source/Brain/version references. A successful public release advances only the production pointer/generation. A failed package, build or deployment preserves the last-good pointers.

Separate packaging and release worker processes keep the Vercel token outside the API, source provider, builder and generated runtime. The release service uploads only validated Build Output API files, stages a **production** deployment with domain assignment disabled, checks its exact marker/page, checks the expected routing/base/session, promotes, observes actual routing/public health, and then commits the pointer. It never requests a provider source rebuild. A failed/canceled post-promotion update restores the prior approved deployment and verifies restoration; a failed first release removes only its own observed alias.

A stable command receipt/key survives uncertain HTTP outcomes. Duplicate keys and equivalent logical commands converge. Pending provider writes are persisted before dispatch. Unknown create/promotion/restore outcomes are observed using their saved identities; missing observations never justify a blind repeat. Definitive provider rejections are distinguished from uncertain writes. Confirmed failed packaging/deployments have explicit reviewed retries that retain old failure history. Owner-requested observation recovery renews only a bounded read budget, retaining the original action/deadline. Ambiguous routing or duplicate physical resources block further promotion.

Worker leases fence state commits. Project-before-operation locking coordinates cancellation and publication. Release/packaging concurrency defaults to one and is globally fenced in PostgreSQL; configured capacity is bounded to 1–4. Operations have a 60–1,200 second configured deadline, at most 120 release ticks and 60 target-observation attempts. Source/configuration, cancellation, expiry and identity are rechecked after public health under the pointer-commit lock. Cleanup failures retain their container identity and are retried.

## Runtime setup

1. Install locked dependencies, back up the existing database, stop conflicting workers, and run `uv run --locked alembic upgrade head` from `apps/api`. Readiness requires `0006_release_hardening`. Never apply a destructive downgrade after source/release/evidence history exists. Recover using compatible current code with release support disabled, or a tested metadata restore; an old Phase 2B API reports the newer schema as unready.
2. Provision the existing `next-web-v1` recipe using a reviewed official Node 24 digest and its existing script. Run fresh exact-image containment/execution acceptance. Derive production with `apps/api/.venv/bin/python scripts/provision-production.py --base-image-id sha256:…`. Image creation is not acceptance.
3. Run `scripts/test-backend.py --docker --production --image-id sha256:… --socket /private/worker/docker.sock`. It emits `.runtime/production-acceptance-report.json`; all three checks must pass. Each host/architecture/image needs its own report. The accepted macOS-hosted Linux arm64 image in this continuation is recorded in `QA/commercial-v1/docker.json`.
4. Supply `EXECUTION_MODE=real`, `REAL_EXECUTION_ENABLED=true`, the accepted `SANDBOX_IMAGE_ID` and matching `SANDBOX_ACCEPTANCE_REPORT`, plus `RELEASE_ENABLED=true`, `PRODUCTION_IMAGE_ID` and matching `PRODUCTION_ACCEPTANCE_REPORT`. Set the worker-owned `SANDBOX_SOCKET`, isolated `PREVIEW_ORIGIN` and exact `FACTORY_ORIGIN`. Real intent can be saved while execution/release support is disabled; unavailable capabilities are not fabricated.
5. Run `python -m f01.execution.worker`, `python -m f01.release.packaging`, and `python -m f01.release.worker` in separate services. Give **only the release service** `F01_VERCEL_TOKEN` and, for a team-scoped account, `F01_VERCEL_TEAM_ID`. Keep the token in the service secret store, never source, frontend variables, a Docker image, or builder environment. Keep generated-app projects separate from factory hosting. Operator credentials need authority only for their intended release account/projects.
6. The owner selects **Set up production hosting** after the first verified preview. The release worker creates/correlates `f01-{project UUID}` in its configured account, then persists its validated provider project and default HTTPS alias. It refuses an unrelated pre-existing binding. Prepare the production package, review the version, check the publication confirmation, then Deploy. Production has no generated database, uploads, app secrets or deployment hooks. A package requiring server features fails rather than silently changing scope.

Public URLs must be exact HTTPS `*.vercel.app` tenant origins and distinct from the factory host. Health uses a credential-free client, public-address DNS checks, bounded bodies, no redirects, no cookies, and exact saved marker/page bytes. `vercel.app` is listed in the [Public Suffix List](https://publicsuffix.org/list/public_suffix_list.dat), so separate provider tenants are separate browser sites. The preview iframe keeps `allow-scripts` without same-origin permission and sends no referrer.

## Operational limits and evidence

The workspace shows recent preparations/packages/releases; owned historical `GET /releases/{id}` and `GET /release-artifacts/{id}` remain addressable beyond that window. Provider URLs can expire or be deleted independently of retained database history/package bytes. No application-data rollback is claimed. PostgreSQL backup must include package bytes and metadata; the real dump/restore regression verifies populated source/release history, package digests and the migration version.

For a stuck release, inspect its state and immutable IDs before any action. **Resume provider observation** never changes a pending write identity. Use **Retry reviewed deployment** only for a confirmed terminal failure/cancellation and current package/bases. A routing conflict, missing correlation or exhausted target setup observation needs operator review in the bound provider account; do not edit the production pointer or adopt an unrelated project. Revoke a compromised credential in its secret store/provider, retain evidence, and reobserve outstanding actions before allowing further releases.

CI runs backend regression, strict mypy, contract/client drift, frontend/client tests, typecheck, production build and browser regression. Exact-image Docker acceptance is separately dispatched with an explicit reviewed base digest; live provider acceptance is an opt-in disposable run. CI configuration is not itself a passing remote-run claim.

Final local acceptance and the dedicated Reliability Pass are recorded in `QA/commercial-v1/VERIFICATION.md` and the selected machine-readable reports. Real Vercel staging, public health, redeploy, previous-package restoration, and a fresh credential-free public browser probe are observed acceptance gates. The provider test deletes only its disposable project afterward; its recorded URLs are evidence, not ongoing hosted customer products. OIDC browser identities and model responses in the controlled tests are explicitly synthetic; no live OpenAI/model-quality result is claimed.
